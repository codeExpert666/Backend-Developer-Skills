VaultRAG 是一个面向中文技术 Markdown 与 Obsidian 笔记仓库的本地、只读、证据优先知识问答项目。它不把“大模型能读笔记”当作完成标准，而是把文件摄取、增量索引、混合检索、引用校验、拒答、评测和开源交付组成一条可重复验证的工程链路。

项目公开定位统一使用：

> 受个人技术笔记场景启发，使用合成示例仓库独立设计与实现的本地知识问答项目。

个人笔记仓库只作为私有验收目标，不进入公开代码、测试夹具、截图、日志、制品或 Issue。公开仓库使用结构相似但内容完全合成的 demo vault。

> [!important] 当前状态
> 本组笔记是 2026-08-29 建立的候选项目设计。截至该时间，尚未创建 VaultRAG 代码仓库，也没有构建、测试、评测、性能、发布或用户使用证据。文中的命令、模块、版本与门槛均表示拟实现合同或待验证候选，不得描述为既有成果。

## 一句话问题

普通聊天界面可以把若干笔记塞进上下文，却很难持续回答以下问题：

- 仓库变化后，哪些文档和切片真正被更新或删除？
- 回答中的每个事实到底来自哪个文件、标题和文档版本？
- 精确命令、错误码与配置项是否会被纯语义检索漏掉？
- 笔记没有答案、内容冲突或已经过期时，系统能否明确拒答？
- 本地模型、Prompt、切片或检索参数变化后，质量是否退化？
- 如何证明程序只读取笔记，而没有静默改写或泄露私人内容？

VaultRAG 的核心价值是把这些问题变成确定性合同，而不是包装一个“上传文件后聊天”的界面。

## 核心产品合同

一次成功回答必须同时满足：

1. 输入问题与检索范围被明确记录。
2. 证据来自当前活动索引中的真实 Markdown 切片。
3. 回答中的可核查主张关联一个或多个有效证据标识。
4. 引用能定位到相对路径、标题层级和源内容版本。
5. 程序校验引用，不接受模型自造的文件名或证据标识。
6. 证据不足时返回明确拒答，不用模型常识补齐仓库事实。
7. 源仓库在索引和问答前后保持不变。
8. 模型、Prompt、解析器、切片器、索引和评测集版本可追踪。

这与 [[AI 应用开发的系统分层与职责边界]] 中“概率性能力服从确定性系统”的原则一致。

~~~mermaid
flowchart LR
    V["只读 Markdown / Obsidian Vault"] --> I["摄取与增量索引"]
    I --> L["关键词索引"]
    I --> E["向量索引"]
    Q["用户问题"] --> R["混合检索与证据组装"]
    L --> R
    E --> R
    R --> M["Ollama 模型适配"]
    M --> C["结构、主张与引用校验"]
    C --> A["回答、拒答或冲突终态"]
    A --> O["CLI / 本地 HTTP"]
    A --> T["评测与运行证据"]
~~~

源文件是权威事实；关键词索引、向量索引、缓存和回答记录都是可删除、可重建的派生数据。具体边界见 [[Embedding、向量索引与派生数据边界]]。

## 已确定原则与待验证候选

| 类型 | 当前结论 |
| --- | --- |
| 产品形态 | 单用户、本地优先、只读知识问答 |
| 首要语料 | UTF-8 Markdown，兼容常见 Obsidian Frontmatter、Wikilink、Callout 与代码块 |
| 主实现语言 | Go 单体与 CLI，优先交付单二进制和清晰模块边界 |
| 推理入口 | Ollama-first，通过本地能力合同隔离模型名称和 API 细节 |
| 检索主线 | 关键词与向量并行召回，经确定性融合、去重和上下文组装 |
| 证据原则 | 应用生成证据标识，模型只能引用候选证据，最终由程序校验 |
| 数据位置 | 索引与运行数据位于 vault 外部，不向源仓库写缓存或元数据 |
| 首发入口 | CLI；本地 HTTP 服务和第三方聊天界面适配后置 |
| 公开数据 | 只使用合成 demo vault 与合成评测集 |
| 依赖选择 | Markdown 解析器、元数据存储、关键词与向量实现需通过小型技术验证后锁定 |
| 非目标 | 写回笔记、多用户 SaaS、任意工具 Agent、GraphRAG、训练或微调模型 |

“候选”不等于可以无限延期。[[VaultRAG 迭代实施与开源交付路线图]] 为每项候选设置技术验证与退出条件。

## 为什么适合做成小型开源项目

这个项目的规模足以形成完整作品，又能把复杂度控制在个人可交付范围：

- 问题真实且容易演示：本地笔记难以做持续、可信的知识问答。
- 后端工作清晰：文件系统、解析、索引、数据合同、并发、API、测试和发布都可验证。
- AI 工作不是装饰：检索、引用、拒答、评测和安全都影响产品合同。
- 公开边界明确：个人 vault 永不进入仓库，合成数据可以复现全部主线。
- 可以阶段交付：先完成确定性搜索，再增加向量、回答和界面兼容。
- 竞争力来自证据，而不是模型或中间件清单。

项目必须避免退化成一份 Docker Compose 配置。即使采用现成模型与索引库，摄取语义、增量状态、引用合同、评测集和只读安全仍由 VaultRAG 自己定义并测试。

## 成功标准

项目完成不以“模型回答看起来不错”判断，而以以下证据判断：

- fresh clone 可以按文档在受支持平台构建并运行。
- demo vault 可以从空状态完整索引，也可以正确增量新增、修改、删除和重命名。
- 精确词、语义改写、跨文档综合、无答案、冲突与恶意内容用例可重放。
- 每个引用都能映射回活动源版本；无效引用不会显示给用户。
- 私有 vault 不出现在仓库、日志、测试快照、Release 或错误报告中。
- 源文件写入和越界读取测试为零容忍。
- 模型不可用时，搜索仍可使用；回答返回明确失败而非伪造结果。
- 性能和质量数字绑定代码 revision、数据集、配置、模型和硬件说明。

## 当前下一步

文档确认后，第一步不是接入大模型，而是建立独立代码仓库、合成 demo vault 和阶段 0 验收。随后先交付可测试的扫描、解析、Manifest 和关键词搜索，再引入 Embedding 与回答生成。

在代码仓库出现之前，不创建空的执行记录；实际版本、提交、命令、评测和发布证据应在每个里程碑完成后再写入日期化执行记录。
