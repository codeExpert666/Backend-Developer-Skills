本文规定 VoiceInsight 如何与原工作经历分开表述，如何准备演示与证据，以及不同完成阶段可以写入简历的内容。所有模板都必须替换为当前 release 能重新生成的真实结果；方括号内容是待填字段，不是建议编造的数字。

项目定位见 [[VoiceInsight 项目实践总览]]，实现与发布门槛见 [[VoiceInsight 迭代实施路线图]] 和 [[VoiceInsight 工程质量、验证与交付标准]]。

## 最重要的真实性边界

简历应明确分为两段：

### 工作经历

只写在职期间真实完成并能解释的内容，例如：

- 按基础设施、公共能力和业务模块整理后端结构，降低跨板块重复与文件散乱。
- 建立业务异常、错误码、统一响应和全局异常处理。
- 为请求生成关联 ID，配置日志落盘与轮转，改善问题定位链路。
- 抽取 Excel 图片处理、文件存储等跨模块能力。
- 为前后端补充 Dockerfile 与开发、生产 Compose 配置。
- 完成具体需求和故障定位，并说明自己实际承担的范围。

没有在任职期间完成的数据爬取、AI 分类、Agent、自动报告、告警和细粒度权限，不能写成工作成果。

### 个人项目

VoiceInsight 应表述为：

> 基于真实用户反馈分析工作流抽象、使用合成数据独立设计与实现的个人项目。

不能写成：

- “负责公司舆情平台重构为 VoiceInsight”。
- “服务公司内部多个业务板块”——除非描述的是原工作项目且范围真实。
- “上线后提升分析效率”——个人项目没有真实用户和生产对照。
- “承载百万级生产数据”——生成负载测试不是生产数据。

这种诚实区分不会削弱项目，反而能证明你理解知识产权、证据和工程边界。

## 为什么 VoiceInsight 比继续包装原项目更合适

原工作经历的价值是业务背景、真实协作和问题意识，但无法通过公开代码证明全部实现。VoiceInsight 的价值是把这些问题重新抽象为：

- 可公开复现的领域模型和合成数据。
- 有测试的导入、权限、指标和异步链路。
- 可测量的 Java / Go 工程分工。
- 有评测、安全和降级证据的 AI 应用。

因此，面试叙事应是“工作中看到了什么问题 → 为什么不能直接复制内部系统 → 个人项目如何重新设计 → 哪些结论有公开证据”，而不是贬低原项目为“玩具”或把个人项目伪装成公司产物。

## 三个可投递版本

不必等待全部 Agent 能力完成才投简历。

| 版本 | 最小完成门槛 | 适合强调 |
| --- | --- | --- |
| A：后端业务闭环 | 项目阶段 0～3 | Java、Spring、MySQL、权限、数据导入、指标与测试 |
| B：工程增强 | 项目阶段 0～5 | Java / Go 分工、Outbox、Kafka、Elasticsearch、可观测性、恢复 |
| C：AI 增强 | 项目阶段 0～8 中所选 AI 能力 | 结构化输出、评测、RAG、Tool Calling、受控 Agent 与安全 |

版本 A 足够成为优质后端项目；版本 C 是增量，不应成为求职启动条件。

## 简历项目标题

候选标题：

> VoiceInsight——多源用户反馈智能分析平台（个人项目）

副标题可以按实际版本选择：

- 版本 A：Java 后端、数据治理与指标分析。
- 版本 B：Java / Go 多语言异步数据平台。
- 版本 C：带受控 Agent 的用户反馈分析平台。

不要在标题中罗列所有中间件。

## 项目简介模板

只有相应能力真实完成后才使用：

> 基于真实用户反馈分析工作流抽象的个人项目，使用合成数据统一管理市场反馈、Beta 问题与问卷，提供可追溯导入、产品数据范围权限、NPS / NSS 指标和 Top 问题分析；后续通过 Java / Go 异步处理、全文检索与受控 AI 工具生成有证据的分析和报告草稿。

如果只完成版本 A，应删除“Java / Go 异步处理、全文检索与受控 AI”部分。

## 版本 A 简历要点模板

每条要点后都有准入条件；条件未满足就不使用。

### 业务与领域

> 设计产品、特性树、反馈、问卷、评分口径与导入任务等领域模型，以版本化指标定义统一 NPS / NSS 的区间、分母和生效规则，并通过固定合成数据验证聚合结果。

准入条件：迁移、代码和自动化测试真实存在，NPS / NSS 期望结果可重放。

### 导入可靠性

> 实现带幂等键、行级错误、部分成功、取消和重试语义的数据导入管道，在 [数据集与硬件] 下处理 [实际记录数或文件大小]，峰值内存、吞吐和错误定位结果记录于性能报告。

准入条件：不能只测成功文件；重复、损坏、取消和恢复用例通过，数字可复现。

### 权限

> 将 RBAC 操作权限与产品数据范围分离，在查询、导出和聚合层统一注入服务端授权范围，并用端到端测试验证跨产品访问被拒绝。

准入条件：拒绝测试覆盖真实 MySQL 查询，不能只有前端隐藏按钮。

### SQL 与性能

> 针对时间、产品、特性和来源组合查询设计索引与稳定分页，通过 `EXPLAIN ANALYZE` 和负载测试将 [具体查询] 的 P95 从 [基线] 优化到 [结果]，同时记录写入代价与适用数据分布。

准入条件：必须有优化前后同环境、同数据、同请求组合的报告；没有结果时删除数字句。

## 版本 B 简历要点模板

### Java 与 Go 分工

> 采用 Java 模块化单体保存权限、事务与分析权威事实，使用 Go Worker 处理来源连接、文件规范化和有界并发任务，通过版本化 Manifest 与事件契约隔离语言和进程边界。

准入条件：Go 不是空服务，存在取消、背压、竞态与集成测试。

### 事件一致性

> 通过 Transactional Outbox 发布反馈、分类和搜索事件，消费者以事件 ID 与业务版本实现幂等，覆盖数据库提交后发布失败、重复投递、乱序和重放场景。

准入条件：Outbox 和 Kafka 已真实运行，故障测试和恢复记录可定位。

### 搜索

> 将 Elasticsearch 作为可重建搜索投影，组合全文、结构化过滤与 [实际完成后再写混合检索]，实现索引版本、别名切换、权限前后双重过滤和全量重建演练。

准入条件：能从 MySQL 重建并比较数量、抽样内容和越权结果；未完成向量检索时删除括号内容。

### 可观测与恢复

> 使用 OpenTelemetry 关联 Java HTTP、Kafka、Go Worker 与搜索链路，建立导入状态、消费 Lag 和错误分类指标，并完成发布回滚、MySQL 恢复和搜索重建演练。

准入条件：存在实际 Trace、指标和日期化恢复记录，不能只写配置文件。

## 版本 C 简历要点模板

### AI 分类

> 使用严格 JSON Schema 输出问题与特性候选，保存模型、Prompt、分类树和反馈修订版本；在 [评测集版本与规模] 上报告 Macro-F1、各类别召回、弃权与人工修正结果。

准入条件：评测数据、评分代码、模型快照和结果报告完整；不能只展示三条成功样例。

### 自然语言分析

> 将自然语言请求映射为受限指标与证据工具，服务端注入身份、产品范围、时间和结果上限，避免模型直接生成 SQL；固定评测中数值由确定性服务计算，越权泄漏和虚构执行结果为 0。

准入条件：工具选择、参数、权限和数值一致性都有自动评测；硬安全失败为零。

### RAG 与 Agent

> 区分结构化指标工具与文本 RAG，使用可追溯反馈引用回答“Top 问题及证据”，为只读 Agent 设置步骤、超时、Token、成本和工具白名单，并验证取消、无答案和提示注入场景。

准入条件：Agent 状态机、Trace、引用评测和攻击集真实存在；没有 MCP 时不写 MCP。

## 不建议的简历写法

| 写法 | 问题 | 应如何改 |
| --- | --- | --- |
| “采用 Spring Boot、Go、Redis、Kafka、ES、Docker、K8s、AI 等技术” | 技术清单没有问题与结果 | 写清某个业务问题、选择、失败边界和证据 |
| “实现智能舆情分析，准确率 95%” | 指标、数据、类别和计算方式不明 | 写评测集版本、任务、指标、基线和失败类别 |
| “使用 Redis 提升性能” | 没有缓存对象、一致性和测量 | 写热点、TTL、回源、失效和前后 P95 |
| “使用 Kafka 保证数据一致性” | Kafka 本身不能完成跨系统事务 | 写 Outbox、至少一次、幂等、重放和死信 |
| “实现微服务架构” | 可能只是多个容器，没有边界与收益 | 写为何拆 Go Worker、所有权、契约和故障隔离 |
| “Agent 自动查询数据库并生成报告” | 暗示任意 SQL、越权和不可复核 | 写受限工具、确定性数值、引用和人工发布 |
| “项目支持百万数据或高并发” | 合成负载不等于生产使用 | 写指定环境下的生成数据和测试结果 |

## 公开仓库应具备的材料

### 第一屏

- 一句话问题与产品价值。
- 当前完成版本 A / B / C 和明确未实现项。
- 一张边界清晰的架构图。
- 最短启动、初始化和演示入口。
- 演示数据完全合成的声明。

### 工程证据

- OpenAPI、数据库迁移与领域图。
- Java / Go 目录职责和共享契约。
- CI 状态与质量门禁说明。
- 导入、权限、指标、消息、搜索和 AI 的测试入口。
- 性能、评测、Trace、故障和恢复报告索引。
- ADR、已知限制、升级与回滚说明。

### 安全与合规

- 无真实公司资产、数据、内部名称和凭据的说明。
- 文件、PII、导出、连接器、模型和 Prompt 的威胁模型。
- 依赖许可证、SBOM 和秘密扫描结果。
- 公开演示账号只使用最小权限与可重置合成数据。

## 十二分钟演示脚本

### 0～2 分钟：问题与边界

- 说明多来源反馈为什么难以可信分析。
- 明确 VoiceInsight 是受真实业务启发的个人项目，数据全部合成。
- 指出 Java 权威业务与 Go Worker 的分工。

### 2～5 分钟：数据进入

- 提交含正常、错误和重复行的文件。
- 展示任务状态、行级错误、幂等结果和来源追踪。
- 说明取消和部分成功的实际语义。

### 5～7 分钟：权限与指标

- 用授权账号查看 NPS / NSS、Top 问题和证据。
- 展示指标口径版本、样本量和时间范围。
- 用无权账号访问另一个产品，展示一致拒绝。

### 7～9 分钟：工程链路

- 展示 Java 到 Kafka、Go Worker 和 Elasticsearch 的 Trace。
- 关闭一个依赖，展示确定终态、Lag 或降级。
- 指向恢复或重建 Runbook，而不是现场执行危险恢复。

### 9～11 分钟：AI 增量

- 展示一条结构化分类候选及人工修正。
- 提问 Top 问题，展示工具参数、确定性数值和引用。
- 输入越权或提示注入样例，展示拒绝和 Trace。

### 11～12 分钟：证据与取舍

- 打开测试、性能或评测报告。
- 说明为什么没有首发 Kubernetes、多 Agent 和 Text-to-SQL。
- 说明当前限制和下一个重评条件。

演示只展示当前版本已完成部分；版本 A 不需要伪造后四分钟内容。

## 面试叙事结构

对每个技术点使用同一结构：

1. **问题**：业务或故障是什么。
2. **约束**：权限、数据、一致性、成本或个人项目限制是什么。
3. **候选**：比较过哪些方案。
4. **决定**：当前选了什么，为什么没有选更复杂方案。
5. **失败**：至少一个真实失败或边界用例。
6. **证据**：测试、SQL 计划、指标、Trace、评测或恢复记录。
7. **重评**：什么条件出现时会更换设计。

这种叙事比背诵中间件原理更能证明独立工程能力。

## 面试前必须能回答的问题

- 为什么以模块化单体开始，哪些证据才会触发拆分？
- Java 与 Go 为什么这样分工，Go 服务不是为了简历关键词吗？
- 如何区分上传幂等、来源重复和语义相似？
- NPS / NSS 的分母、量表、时区和口径版本如何处理？
- Redis 不可用时业务是否正确，缓存如何防止跨产品泄漏？
- Outbox 解决了哪一段双写问题，还有哪些“恰好一次”做不到？
- Kafka 重复、乱序、积压和重放如何处理？
- Elasticsearch 为什么是派生数据，如何重建和回退？
- 文件导入如何防 ZIP Slip、压缩炸弹、路径穿越和公式注入？
- Agent 为什么不用 Text-to-SQL，工具身份和产品范围从哪里来？
- Structured Outputs 能保证什么，不能保证什么？
- AI 质量如何评测，为什么不能只写一个准确率？
- 模型、搜索或 Go Worker 失败时，用户看到什么、系统如何恢复？
- 简历中的每个数字能否在当前 release 重跑？

如果某个要点无法回答，应先补实现和证据，而不是润色简历。

## 与 EventHub 的取舍

[[EventHub 项目实践总览]] 可以继续作为活动票务和双语言语义复刻的学习项目，但求职简历不宜同时放两个未完成的大项目。

当前建议：

- VoiceInsight 作为与工作背景最连贯的主要展示项目。
- EventHub 保留为学习、源码或特定工程能力的补充证据。
- 如果 EventHub 的完成度显著高于 VoiceInsight，可先投递 EventHub 的真实版本；不要为追求新故事隐藏已有完成成果。
- 最终只选择能在面试现场打开代码、运行测试并解释失败边界的项目。

## 求职节奏

1. 完成版本 A 后立即形成第一版项目条目并开始投递。
2. 投递过程中继续完成版本 B，把真实面试问题转成补强项。
3. AI 能力以分类和自然语言只读分析为先；不因追求“完整 Agent”推迟求职。
4. 每次简历更新绑定一个 release，保留上一版可重放证据。
5. 如果时间有限，优先级是：正确业务与权限 > 测试与 SQL > 导入可靠性 > 观测与恢复 > 搜索与消息 > AI > Kubernetes。

项目的竞争力来自可解释、可验证和可迁移，不来自目录数量或依赖数量。
