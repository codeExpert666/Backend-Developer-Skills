AI 评测的目标不是证明模型“聪明”，而是用固定任务、数据、版本和判断规则回答：某次变更是否仍满足产品合同，哪些用例退化，以及是否允许发布。

## 从能力合同开始

先把“效果好”改写成可判断的合同：

- 输入是什么，哪些字段来自权威事实。
- 输出必须具备什么结构和业务约束。
- 哪些波动可以接受，哪些错误绝不允许。
- 需要检索、引用或工具时，正确链路是什么。
- 无答案、无权限、取消和依赖不可用时应该怎样结束。
- 哪些项目可以自动判断，哪些需要人工标注。

模型表达的开放性不等于成功标准也必须模糊。结构、事实字段、权限和工具副作用通常可以确定性检查；措辞质量和帮助程度则可以用明确量表人工评估。

## 评测集的数据结构

每条用例至少包含：

| 字段 | 作用 |
| --- | --- |
| `case_id` | 稳定定位失败与历史结果 |
| 输入与可信上下文 | 重放真实任务，不包含秘密和无必要个人数据 |
| 预期结构或参考事实 | 作为自动断言和人工判断依据 |
| 允许与禁止行为 | 明确安全、拒答和副作用边界 |
| 人工标签 | 相关资料、理想工具、质量等级或风险分类 |
| 数据来源与版本 | 说明用例对应哪一批资料和业务规则 |
| 重要等级与分组 | 防止平均分掩盖关键失败 |

数据至少分为日常开发集和独立回归集。调 Prompt 或参数时反复查看的数据已经参与优化，不能继续充当完全独立的发布证据。生产失败样例应脱敏、复核后加入回归集，并保留最初失败分类。

## 一次运行必须锁定版本坐标

```text
评测运行 = 能力合同版本
         + 应用 revision
         + 模型与模型快照
         + Prompt 版本
         + 输出 Schema 版本
         + Tool Schema 与工具实现版本
         + 数据集与标注版本
         + 检索资料、切分、Embedding、索引版本
         + 评测器与阈值版本
         + 运行环境和时间
```

只记录模型名或只保存平均分都无法复现。供应商默认别名、索引内容和在线资料会变化，应在实际评测记录中固定当次值；长期知识笔记不写死默认模型。

OpenAI 核对日的官方文档已经公布旧 Evals 平台和可复用 Prompt 对象的迁移/关停时间线。因此本路线以工具无关的文件、代码、Git revision 和可重放运行清单为事实来源，不把某个将退役的平台对象当作唯一版本记录。

## 分层指标

| 层级 | 可用指标或断言 | 不能替代什么 |
| --- | --- | --- |
| 结构 | JSON 解析、Schema、必填字段和枚举通过率 | 业务事实正确性 |
| 事实 | 权威字段逐项一致、数值与日期约束 | 开放文本帮助程度 |
| 检索 | Recall@K、MRR、过滤正确率 | 最终答案有据性 |
| 引用 | 引用存在、主张支持、来源版本正确 | 检索是否覆盖所有资料 |
| 工具 | 工具选择、参数、授权、结果和副作用正确率 | 最终自然语言质量 |
| 安全 | 越权、注入、泄露和危险操作拦截率 | 正常用例可用性 |
| 运行 | 错误率、取消、首 Token 和总延迟、Token 与成本 | 内容质量 |
| 人工质量 | 相关性、完整性、清晰度和可行动性量表 | 可自动验证的硬约束 |

指标必须按重要等级、场景和语言分组报告，同时保存逐用例结果。一个高平均分不能抵消“越权写操作成功”这样的阻断性失败。

## 评测器也需要验证

规则评测器应有单元测试；模型评测器需要固定指令、量表、参考证据和自身版本，并抽样与人工判断比较。不要让同一个未经校准的模型既生成答案又裁定自己正确。

人工标注需要：

- 简短、可执行的标签定义和正反例。
- 对关键样例双人复核或冲突仲裁。
- 保存标注人、时间和规则版本，而不是只覆盖最终标签。
- 区分“资料没有答案”和“系统没有找到答案”。

## 回归门禁

门禁在运行前声明，至少包含：

1. 阻断性用例必须全部通过，例如权限、Schema、重复副作用和秘密泄露。
2. 核心质量指标不得低于绝对阈值。
3. 与当前生产基线相比，退化不得超过允许范围。
4. 延迟、Token、成本和错误率不能越过资源预算。
5. 失败样例和统计不确定性经过人工复核。
6. 运行清单、原始结果摘要和差异可以重放。

门禁失败时保留证据并停止发布。不能删除困难用例、临时降低阈值或只重跑到偶然通过。

## 发布、灰度与回滚

通过离线评测不等于已经通过生产验证。安全发布顺序是：

- 使用功能开关把 AI 能力与确定性主链路隔离。
- 先影子运行或小流量灰度，验证真实分布、延迟和依赖错误。
- 明确新旧版本的路由单位，避免同一会话混用不兼容 Prompt 或 Schema。
- 持续比较关键指标和失败类型，达到停止条件自动回退。
- 回滚应用、Prompt、模型路由和索引时使用同一版本清单。
- 保留新格式产生的数据兼容或迁移策略，不能只回滚代码。

可复现交付至少包含：代码 revision、依赖锁、配置 Schema、Prompt/Tool/输出契约、数据集版本、索引构建说明、评测命令、结果摘要、发布门槛、功能开关和恢复步骤。

## Java 与 Go 的共同证据

- 两端共享产品级能力合同、JSON/JSONL 用例、权威事实、工具语义和门禁阈值。
- 语言专属单元测试验证各自序列化、取消、异常/错误和并发实现。
- Java 先形成正式能力基线后，Go 使用同一输入与预期复刻；不要求模型逐字输出一致。
- 对照结果必须标记实际 SDK、框架和运行时版本，不能把某端跳过的测试写成通过。

## 完成检查

- 每个质量结论都能回到用例、标签、版本和原始结果。
- 正常、失败、无答案、权限和取消场景都在固定集中。
- 结构、事实、检索、引用、工具、安全和运行指标没有混成一个总分。
- 门禁在结果出现前定义，阻断性失败不能被平均分抵消。
- 发布和回滚使用可定位版本，不依赖控制台里未导出的临时状态。
- “评测已通过”只描述本次运行证据，不等于用户已经掌握或生产已经验收。
