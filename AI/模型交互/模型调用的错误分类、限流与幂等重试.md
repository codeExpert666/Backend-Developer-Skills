可靠重试不是“捕获异常后再调用一次”。模型调用具有成本、概率性输出、流式部分结果和潜在工具副作用，必须先判断失败发生在哪一层、远端是否可能已经处理，再决定是否、何时以及以什么身份重试。

## 先建立错误分类

| 分类 | 常见信号 | 是否通常可重试 | 关键判断 |
| --- | --- | --- | --- |
| 本地输入或配置 | 缺少参数、Schema 非法、输入过大 | 否 | 修复请求后才是新调用 |
| 认证 | 401、凭据失效 | 否 | 不要用重试掩盖密钥或配置错误 |
| 授权 | 403、无资源权限 | 否 | 重新鉴权或修正权限范围 |
| 资源与冲突 | 404、409 | 视业务语义 | 资源是否刚创建、并发更新是否可安全重放 |
| 限流 | 429、速率响应头 | 是，需限次退避 | 区分瞬时速率限制与额度耗尽 |
| 供应商服务 | 5xx、过载 | 是，需限次退避 | 结合状态页、总预算和熔断 |
| 网络或超时 | DNS、TLS、连接重置、读超时 | 条件性 | 远端是否可能已收到并处理 |
| 用户取消 | 本地取消、截止时间到期 | 通常否 | 尊重用户意图，不自动重启 |
| 流式协议与结果 | 流中断、事件非法、整体不完整 | 条件性 | 能否查询/续接，部分输出如何处置 |
| 业务校验 | 事实冲突、越权、状态过期 | 通常否 | 重新读权威状态，而不是盲目再生成 |

HTTP 状态只是线索。SDK 异常可能包装网络原因，429 也可能代表完全不同的“请求太快”或“额度不足”。适配层应把供应商错误映射为稳定的本地类别，并保留原始请求 ID 供排查。

## 重试前回答五个问题

1. 请求在本地失败，还是远端可能已经接受？
2. 当前错误是短暂故障，还是输入、认证、权限或合同错误？
3. 重试会不会产生新的计费、不同模型结果或重复工具副作用？
4. 剩余总时限、Token/成本预算和尝试次数是否允许？
5. 有无任务 ID、幂等键或查询接口可以先确认状态？

任意一项无法回答时，默认不要立即重发；先记录 `UNKNOWN`、查询或对账。

## 限流不是固定睡眠

OpenAI 官方限流指南建议使用带随机抖动的指数退避，并设置最大重试次数；失败请求本身也会占用每分钟限额，因此无上限地快速重发只会恶化问题。

一个供应商无关的退避策略应包含：

- 最大尝试次数和总截止时间。
- 指数增长的等待时间。
- 随机抖动，避免多个实例同时再次请求。
- 对供应商 `Retry-After` 或速率重置提示的受控采纳。
- 请求级并发限制和队列长度上限。
- 超过预算后的明确降级，而不是后台无限等待。

还应读取速率响应头，区分请求数与 Token 限制。具体头名称属于供应商合同；OpenAI API 当前提供请求、Token、剩余额度与重置时间等速率头，使用时按官方参考核对。

## 幂等需要覆盖“逻辑请求”，不只是 HTTP

模型生成通常不是天然幂等：同样输入重新调用可能得到不同输出，也可能再次计费。若后续还有工具调用，重复执行甚至会造成业务副作用。

建议区分三个标识：

| 标识 | 生命周期 | 用途 |
| --- | --- | --- |
| 逻辑请求 ID | 一次用户意图 | 聚合全部尝试，做业务去重与对账 |
| attempt ID | 每次实际调用 | 记录重试顺序、延迟、用量和错误 |
| 供应商请求/任务 ID | 供应商一次处理 | 查询状态、支持排障和关联事件 |

重试只创建新的 attempt，不创建新的用户意图。业务写操作必须使用逻辑请求 ID 或独立业务幂等键去重，并在执行前重新读取最新权限与状态。

### 不同阶段的重复风险

| 失败位置 | 重试风险 | 处理方式 |
| --- | --- | --- |
| 提交前本地校验失败 | 远端未处理 | 修复输入，不计作同一请求重试 |
| 连接建立前明确失败 | 通常未处理，但需看客户端证据 | 可有限重试 |
| 写出请求后读超时 | 远端可能已处理 | 先按请求/任务 ID 查询；无法确认则对账 |
| 收到部分流后中断 | 已产生部分结果与成本 | 不拼接两次输出；能续接则续接，否则丢弃正式结果再重试 |
| 工具执行后模型续接失败 | 副作用已经发生 | 查询工具执行记录，回传原结果，不重复执行 |

工具侧的确认、事务和幂等细节见 [[Tool Calling 生命周期与可靠业务边界]]。

## 一条受控重试算法

```text
校验请求并创建逻辑请求 ID
  → 在总截止时间与成本预算内开始 attempt
  → 调用模型并保存供应商请求或任务 ID
  → 成功：确认完整终态，再做结构与业务校验
  → 失败：映射错误类别，判断远端是否可能已处理
      → 不可重试：立即返回明确错误
      → 状态未知：先查询或对账
      → 可重试：计算带抖动退避，检查剩余预算后开始下一 attempt
  → 超出预算：进入降级或返回可解释失败
```

重试策略应由适配层或统一可靠性组件管理，业务代码只声明调用预算和允许重试的操作类别，不能在多个 Controller 中各写一套循环。

## 流式调用的特殊处理

### 不要把两次流直接拼接

第一次流中断后，第二次生成的内容不一定是第一次的后半段。直接拼接会造成重复句、矛盾结构和非法 JSON。正式结果应来自一个完整 attempt，或来自供应商明确支持且按游标验证的同一后台任务续接。

### 区分错误事件与连接异常

供应商可能通过流内事件报告失败，也可能由 HTTP 客户端报告连接错误。两者都要映射到同一应用终态，但保留来源以便判断是否可查询与重试。

### 部分输出不能触发副作用

在看到整体完成并完成 Schema/业务校验前，不得依据文本增量自动发布内容或执行写工具。相关终态见 [[模型 API 请求生命周期与流式状态]]。

## Java 与 Go 的实现差异

| 关注点 | Java | Go |
| --- | --- | --- |
| 错误映射 | 在适配层解包 SDK 异常及其 cause，映射为本地错误枚举或密封类型 | 使用 `errors.Is` / `errors.As` 检查包装错误，先识别 `context.Canceled` 与 `context.DeadlineExceeded` |
| 退避等待 | 使用调度器或可靠性库，避免占住请求线程；锁定库版本和策略 | 使用 timer 并同时 `select` 上下文取消，不能用不可取消的长时间 `Sleep` |
| 总预算 | 区分业务截止时间、HTTP 超时和 Future 等待时间 | 一个父 `context` 控制总预算；每次尝试可再派生更短超时 |
| 并发限流 | 线程池、信号量、Bulkhead 或应用队列 | 有界 channel、semaphore 或 worker pool，避免无限 goroutine |
| 流错误 | 同时处理订阅完成异常和累积器状态 | 迭代结束后必须检查 `Err()`，并保留已经消费的事件位置 |

两种语言应共享错误分类、可重试矩阵、最大尝试、逻辑请求 ID 和失败 fixture，而不是共享某个重试库的配置文件。

## 可观测与排障

每次 attempt 至少记录：

- 逻辑请求 ID、attempt ID 和供应商请求 ID。
- 本地错误类别、HTTP 状态或流式终态。
- 是否可重试、实际退避时间和剩余尝试。
- 输入/输出 Token、总延迟和本次成本。
- 是否产生部分输出、工具调用或其他副作用。
- 最终是成功、失败、取消、不完整还是未知。

OpenAI 官方 API 参考建议在生产中记录 `x-request-id`；还可以主动发送唯一的 `X-Client-Request-Id`，便于在超时或没有收到响应头时排查。不要在日志中附带 API Key 或完整敏感输入。

观测字段与降级策略见 [[AI 应用的成本、延迟、可观测性与降级]]。

## 故障注入与验证

- [ ] 本地 400 类合同错误不会重试。
- [ ] 认证和权限错误不会通过换 Key 循环掩盖。
- [ ] 429 使用带抖动的有限退避，且失败尝试也计入预算。
- [ ] 额度耗尽与瞬时速率限制具有不同对外提示。
- [ ] 5xx、网络中断和超时都受总截止时间与最大尝试约束。
- [ ] 用户取消会立即停止等待和后续尝试。
- [ ] 首次响应不确定时，系统先查询或对账而不是直接重发。
- [ ] 两次流不会被未经验证地拼成一个完整结果。
- [ ] 工具已经成功执行后，模型重试不会重复副作用。
- [ ] Java 与 Go 对同一故障 fixture 给出相同错误分类和最终语义。

这些场景应进入 [[AI 评测、版本化与发布门禁]]，避免 SDK、模型或代理配置变化后重试行为静默改变。
