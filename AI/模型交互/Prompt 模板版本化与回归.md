生产 Prompt 不是散落在字符串里的“文案”，而是影响模型行为的可执行合同。它应与代码一样经过命名、类型化输入、评审、测试、灰度和回滚，并与模型、Schema、工具和评测集版本共同记录。

## Prompt 合同包含什么

一个完整 Prompt 合同通常由以下部分组成：

| 部分 | 负责内容 | 常见风险 |
| --- | --- | --- |
| 能力目标 | 本次生成要解决什么、不解决什么 | 目标过宽，无法判断成功 |
| 应用指令 | 行为、边界、语气、拒答和优先级 | 与业务规则冲突或依赖过期能力 |
| 动态输入 | 用户问题、结构化事实和任务参数 | 拼接注入、缺少类型和来源 |
| 上下文布局 | 历史、检索资料和工具结果如何分区 | 不可信数据被当成指令 |
| 示例 | 期望格式和边界案例 | 示例事实被模型误当当前事实 |
| 输出合同 | 文本要求、JSON Schema 或工具 Schema | Prompt 与消费者合同漂移 |
| 版本元数据 | Prompt ID、版本、变更原因和兼容范围 | 无法重放或回滚 |

Prompt 只负责向模型表达任务，不能代替权限、事务、业务校验或安全策略。系统分层见 [[AI 应用开发的系统分层与职责边界]]。

## 长期主线：Prompt 随代码和 Git 版本化

生产 Prompt 应保存在应用代码仓库中，可以是专用模块、受版本控制的资源文件或类型化构造函数。推荐的最小结构是：

```text
prompts/
  knowledge_answer/
    prompt.md
    contract.json
    fixtures.jsonl
    README.md
```

这只是职责示意，不要求所有语言使用同一目录形状。关键要求是：

- 每个 Prompt 有稳定的能力名称，而不是按模型名命名。
- 静态指令进入版本控制，动态值通过类型化参数传入。
- Prompt 变更经过 Pull Request 评审，与代码变更一起发布。
- Git commit 能定位实际内容；运行记录另保存业务版本号，便于跨提交比较。
- 同目录或明确引用处保存 Schema、fixture 和评测入口。
- 需要灰度时通过应用配置或功能开关选择已发布版本，不在运行时偷偷改正文。

不要把长 Prompt 复制到多个 Service，也不要让 Controller 通过字符串拼接临时修改系统指令。

## Reusable Prompt Objects 的当前状态

截至 2026-07-27，OpenAI 官方已经宣布弃用 API 中的 Reusable Prompt Objects：

- 2026-06-03 宣布弃用，并在平台中弱化新建 Prompt。
- `v1/prompts` 和 Reusable Prompt Objects 计划于 2026-11-30 停止。
- 官方迁移方向是把 Prompt 内容移入应用代码，以 Git、代码评审、测试和评测管理版本。

因此，新系统不应把平台 Prompt Object 作为长期主线。已有集成应把 Prompt ID、平台版本和变量映射迁回代码，在切换前对旧、新路径执行同一评测集，再删除平台依赖。这里的日期是核对快照；实施迁移时仍应重新查看官方弃用页。

## 模板变量必须是数据，不是字符串替换技巧

### 使用类型化输入

动态输入应先进入本地请求类型并完成校验，再由 Prompt Builder 渲染。至少区分：

- 已验证的应用参数。
- 用户原始输入。
- 经授权的检索资料。
- 工具返回的不可信文本字段。
- 由业务系统提供的权威事实。

不要允许调用方传入“额外系统指令”覆盖固定边界；确需可配置行为时，把它设计成枚举或受控选项。

### 显式分隔指令与资料

Markdown 标题、代码围栏或 XML 标签可以帮助表达区块，但它们只是可读边界，不是安全沙箱。检索资料中的指令仍应被视为数据，并由 [[AI 应用安全威胁建模与防护]] 的注入测试验证。

### 固定前缀与动态尾部

把长期稳定的指令和示例放在前部，把每次变化的用户数据放在后部，有利于阅读、评审，也可能提高依赖精确前缀匹配的 Prompt Cache 命中。缓存行为属于供应商易变实现，不能为了缓存牺牲指令优先级或泄露跨用户上下文。

## Prompt 版本不是一个字符串就够了

一次可重放运行至少要记录：

| 坐标 | 示例语义 | 为什么需要 |
| --- | --- | --- |
| 能力合同版本 | `knowledge-answer/v2` | 标识产品行为与消费者期望 |
| Prompt 版本 | `prompt-v7` | 比较文字与布局变化 |
| Git revision | 完整提交标识 | 定位真实文件内容 |
| Schema 版本 | `answer-schema/v3` | 解释解析和字段变化 |
| 工具合同版本 | `read-tools/v2` | 解释工具选择和参数变化 |
| 模型标识 | 实际请求值 | 解释模型行为变化 |
| 检索配置版本 | 切分、索引和过滤配置 | 解释上下文变化 |
| 评测集版本 | 固定数据 revision | 保证结果可比较 |

Prompt 版本变化但模型或数据也同时变化时，不能把结果差异全部归因于 Prompt。完整版本坐标由 [[AI 评测、版本化与发布门禁]] 统一管理。

## 一次 Prompt 变更的闭环

```mermaid
flowchart LR
    Q["明确失败样例或新需求"] --> C["修改一个可解释因素"]
    C --> R["代码评审与静态检查"]
    R --> E["固定评测集回归"]
    E --> S["安全与失败场景"]
    S --> G["灰度或对照发布"]
    G --> O["观测与人工抽查"]
    O --> K["保留或回滚版本"]
```

### 变更前

1. 写明要改善的具体失败类别，而不是“让回答更好”。
2. 冻结基线模型、Schema、工具和数据版本。
3. 把新失败样例加入评测集，并确认没有包含私人数据。

### 变更中

1. 尽量一次只改变一个可解释因素。
2. 保持动态变量的类型与来源清晰。
3. 检查是否扩大权限、工具范围或上下文采集。
4. 如果输出合同改变，同步评审消费者和兼容策略。

### 变更后

1. 运行结构、事实、引用、工具和安全回归中适用的部分。
2. 比较质量、Token、首 Token 延迟、总延迟和错误率。
3. 记录已知退化，不只报告平均分上升。
4. 通过版本路由或功能开关灰度；保留上一可用版本的快速回滚路径。

## 回归集应该覆盖什么

| 用例类型 | 要防止的退化 |
| --- | --- |
| 典型正常输入 | 基本任务不能完成 |
| 边界与空输入 | 编造字段、无意义长输出 |
| 冲突事实 | 选择无依据来源或忽略冲突 |
| 无答案问题 | 强行生成看似合理的答案 |
| 恶意用户输入 | 覆盖应用指令或索取敏感数据 |
| 恶意检索片段 | 把资料中的指令当系统命令 |
| 结构化输出 | Schema、枚举或必填字段退化 |
| 工具调用 | 选错工具、参数缺失或越权意图 |
| 长上下文 | 遗漏关键约束、截断或成本异常 |

概率性任务不能只断言整段文本完全相等。应把“必须满足、不得发生、允许波动”拆开，组合确定性断言、人工标注和必要的模型评分。

## Java 与 Go 的工程差异

| 关注点 | Java | Go |
| --- | --- | --- |
| Prompt 组织 | 可用资源文件配合不可变输入 DTO，或专用 Builder Bean | 可用 `embed` 固化资源，配合小型构造函数和显式参数 struct |
| 模板引擎 | 引入前确认是否真的需要条件/循环；避免模板拥有业务逻辑 | 优先简单显式构造；使用模板包时严格限定函数与数据来源 |
| 版本注入 | 构建信息、配置和 Bean 可集中暴露当前版本 | 通过构建变量、常量或配置明确暴露版本，不依赖包级可变状态 |
| 测试 | 参数化测试适合大量 fixture，Spring Profile 可做版本路由 | 表驱动测试适合共享 fixture，接口与函数组合便于替换版本 |
| 并发安全 | Prompt Builder 应无共享可变状态，单例 Bean 必须线程安全 | 不复用可变 buffer；函数参数显式，避免全局 Prompt 变量被运行时改写 |

Java 与 Go 可以使用不同模板实现，但同一能力的变量含义、输出合同、禁止项和评测数据必须一致。

## 常见失败与恢复

### Prompt 散落在代码中

先用搜索定位同一能力的所有字符串，建立一个命名 Builder；通过契约测试确认旧入口输出结构，再逐个切换。不要一次性全库替换不同职责的 Prompt。

### Prompt 与 Schema 漂移

将 Schema 版本加入 Prompt 模块和运行记录；CI 在任一方变化时触发共同测试。结构化输出的校验层次见 [[结构化输出的 Schema 与业务校验]]。

### 回归只保留成功案例

恢复真实失败样例和拒答、超时、无答案、越权等场景；历史输出保存在实验产物中，笔记只记录数据位置、版本、指标和结论。

### 新 Prompt 已发布但效果退化

停止扩大流量，通过版本路由回到上一已验证版本；保留失败请求的脱敏标识和版本坐标，定位是 Prompt、模型、检索、工具还是数据变化。

### 已使用平台 Prompt Object

导出并审阅当前内容，把变量转换为类型化函数参数；固定旧路径基线，在代码路径通过同一评测后灰度迁移。不要直接删除旧对象再开始补测试。

## 验证清单

- [ ] 每个 Prompt 对应一个明确能力合同和稳定名称。
- [ ] Prompt 内容与动态参数都在代码评审范围内。
- [ ] 动态输入有类型、来源和校验，不允许任意覆盖应用指令。
- [ ] 运行记录可以定位 Prompt、Git、模型、Schema、工具和数据版本。
- [ ] 固定评测覆盖正常、失败、无答案和恶意输入。
- [ ] Java 与 Go 使用同一产品语义与 fixture，而非逐字输出断言。
- [ ] 灰度和回滚不依赖临时手改线上 Prompt。
- [ ] 新系统没有把已弃用的 Reusable Prompt Objects 当作长期主线。
- [ ] Prompt 和 Trace 中不包含密钥或无必要的私人数据。
