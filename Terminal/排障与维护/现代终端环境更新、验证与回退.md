这篇专题只处理已经搭好的环境：如何一次更新一个层级、用分层证据验证、定位故障并回到已知良好状态。

> [!tip] 何时打开本文
> 安装或迁移尚未完成时，回到所选主线；新机器恢复走 [[从已有 dotfiles 恢复现代终端环境]]。只有环境曾经可用、现在要升级、改配置或排障时，才执行本文。

配置源、Stow 链接与 Git 生命周期见 [[使用 Git 与 GNU Stow 搭建 dotfiles 仓库]]；Zsh 启动和插件依赖见 [[Zsh 与 Antidote 跨机器配置管理]]。

## 1. 把一次维护看成受控事务

一次维护只有四个阶段：

```text
记录基线 → 改变一个层级 → 分层验证 → 提交或回退
```

维护原则：

1. 一次只更新一个层级或一个工具，不使用来源不明的“update all”。
2. 更新前保留一个正常终端或 SSH 会话，新会话通过后再关闭。
3. 二进制按原安装来源更新；配置、插件版本与本地数据分别回退。
4. 更新二进制时不同时重写配置；修改配置时不顺带更新所有插件。
5. 只有新增、移动或删除配置源路径时才需要重新运行 Stow；只改链接指向的文件内容不需要重建链接。
6. 历史、密钥、数据库、插件 clone、缓存和 local 文件不因“备份方便”进入 Git。
7. 新增一个准备由 Stow 管理的组件时，先创建源、部署并验证链接，再把它加入 `.zshrc` 或首次启动应用；维护已搭好环境也要遵守首次写入所有权。

## 2. 更新前记录可比较基线

### 2.1 版本与来源

在正常交互式 Zsh 中记录当前可用版本和实际命令路径：

```zsh
zsh --version

for tool_name in starship atuin zoxide fzf; do
  if (( $+commands[$tool_name] )); then
    printf '%-10s %s\n' "$tool_name" "$commands[$tool_name]"
    "$tool_name" --version
  else
    printf '%-10s missing\n' "$tool_name"
  fi
done

if (( $+commands[ghostty] )); then
  ghostty +version
fi

if (( $+functions[antidote] )); then
  antidote --version
  antidote list
fi
```

版本号只在与命令路径和安装来源一起记录时有意义。PATH 中同时出现两个 fzf 或 Starship 时，应先解决来源冲突，不要继续升级。

### 2.2 配置与链接

```sh
DOTFILES_DIR="$HOME/.dotfiles"

git -C "$DOTFILES_DIR" rev-parse --show-toplevel
git -C "$DOTFILES_DIR" status --short --branch
git -C "$DOTFILES_DIR" diff --check
git -C "$DOTFILES_DIR" log -1 --format=oneline

for managed_path in \
  "$HOME/.zshenv" \
  "$HOME/.config/zsh/.zprofile" \
  "$HOME/.config/zsh/.zshrc" \
  "$HOME/.config/atuin/config.toml" \
  "$HOME/.config/starship.toml"; do
  ls -ld "$managed_path"
  readlink "$managed_path" 2>/dev/null || true
done

starship_profiles_source="$DOTFILES_DIR/starship/.config/starship/profiles"
if [ -d "$starship_profiles_source" ]; then
  for profile_source in "$starship_profiles_source"/*.toml; do
    [ -f "$profile_source" ] || continue
    managed_path="$HOME/.config/starship/profiles/${profile_source##*/}"
    ls -ld "$managed_path"
    readlink "$managed_path" 2>/dev/null || true
  done
fi
unset managed_path profile_source starship_profiles_source

if [ -e "$HOME/.config/ghostty/config.ghostty" ] \
  || [ -L "$HOME/.config/ghostty/config.ghostty" ]; then
  ls -ld "$HOME/.config/ghostty/config.ghostty"
  readlink "$HOME/.config/ghostty/config.ghostty" 2>/dev/null || true
fi
```

已有与本次维护无关的修改时，记录并保留现场，不混入本次提交。`git status` 只能观察仓库，不能发现应用在 `$HOME/.config` 新建的普通文件；因此必须同时看目标类型。若没有已知良好提交、当前 Shell 已经报错或链接来源不明，先恢复基线，不开始更新。

### 2.3 数据层

Atuin 数据、密钥和会话不进入 Git，但升级 Atuin 前可能需要私密备份。先用 `atuin info` 或实际配置确认数据路径；关闭其他会写数据库的 Shell 后再备份。同步用户还必须确认加密密钥可从自己的秘密存储恢复。

zoxide 数据库、原生 Shell 历史和 Ghostty 本机状态也分别属于应用数据，不应因配置提交而被覆盖。

## 3. 选择一个更新对象

| 对象 | 仍使用原来的更新来源 | 更新前的额外检查 | 更新后重点 |
| --- | --- | --- | --- |
| Ghostty | 应用稳定通道、Homebrew cask 或原 Linux 包 | 保留备用终端 | 创建窗口、配置告警、SSH terminfo |
| Zsh | macOS 系统、Homebrew 或 APT | 确认登录 Shell 路径仍存在 | 启动文件、补全、登录与非交互 |
| Antidote 本体与 bundle | 原包管理器或 Git/Antidote 命令 | 保存可恢复 snapshot | 未 pin bundle、加载顺序、启动时间 |
| Starship | Homebrew、APT 或原安装器 | 记录活动配置路径、全部受管配置与 timings | 逐份解析配置、活动 prompt、字体与 Git 仓库性能 |
| Atuin | Homebrew、包管理器或 `atuin update` | 保护数据库、key、session | `atuin doctor`、历史记录与搜索 |
| zoxide | 原包管理器或官方方式 | 保留数据库 | `z`、`zi` 与 fzf 交互 |
| fzf | Homebrew、APT 或 Git 安装目录 | 记录实际命令路径 | `fzf --zsh`、`Ctrl-T`、按键冲突 |
| dotfiles 配置 | Git 工作树中的明确源文件 | 当前 diff 与最近提交 | 语法、真实新会话、秘密边界 |

例如在 Homebrew 中只升级 fzf：

```sh
brew upgrade fzf
```

完成第 5 节全部适用验证后，才选择下一个组件。不要把 `brew upgrade` 全量更新、插件更新与配置重排放进同一次故障域。

## 4. Antidote 更新必须先有版本回退点

Antidote 清单描述加载什么，snapshot 记录某次插件提交集合，两者都不是插件缓存本身。更新前若还没有当前已验证 snapshot，保存到 dotfiles 源：

```zsh
DOTFILES_DIR="$HOME/.dotfiles"
snapshot_source="$DOTFILES_DIR/zsh/.config/zsh/snapshots/antidote.txt"

mkdir -p "${snapshot_source:h}"
antidote snapshot save "$snapshot_source"
```

新增 snapshot 源路径后，先对 `zsh` 软件包模拟并应用 Stow，再审查 Git diff。随后单独更新：

```zsh
antidote update
```

清单中带 `pin:<完整提交 SHA>` 的 bundle 会保持固定。更新后新开 Shell，完成插件、按键和启动性能验证；通过后再覆盖 snapshot 并提交新的已知良好版本。

若修改 `.zsh_plugins.txt`，推荐的 `antidote load` 会在清单较新时处理加载文件。主线把静态加载文件显式放在 XDG cache；当前 Antidote CLI 没有 `antidote refresh` 子命令，不要把不存在的命令写进维护脚本。手工静态模式也应写入缓存：

```zsh
plugin_manifest="${ZDOTDIR:-$HOME}/.zsh_plugins.txt"
plugin_static="${XDG_CACHE_HOME:-$HOME/.cache}/antidote/zsh_plugins.zsh"
mkdir -p "${plugin_static:h}"
antidote bundle < "$plugin_manifest" >| "$plugin_static"
unset plugin_manifest plugin_static
```

生成的 `.zsh_plugins.zsh` 是缓存，不进入 Git。不要在同一配置中混用 `antidote load`、手工 bundle 与旧式初始化。

## 5. 更新后按证据层级验证

### 5.1 第一层：链接与语法

```sh
DOTFILES_DIR="${DOTFILES_DIR:-$HOME/.dotfiles}"
managed_links_ok=1
for managed_path in \
  "$HOME/.zshenv" \
  "$HOME/.config/zsh/.zprofile" \
  "$HOME/.config/zsh/.zshrc" \
  "$HOME/.config/atuin/config.toml" \
  "$HOME/.config/starship.toml"; do
  if [ ! -L "$managed_path" ]; then
    printf 'not a managed link: %s\n' "$managed_path" >&2
    managed_links_ok=0
    continue
  fi
  readlink "$managed_path"
done

starship_profiles_source="$DOTFILES_DIR/starship/.config/starship/profiles"
if [ -d "$starship_profiles_source" ]; then
  for profile_source in "$starship_profiles_source"/*.toml; do
    [ -f "$profile_source" ] || continue
    managed_path="$HOME/.config/starship/profiles/${profile_source##*/}"
    if [ ! -L "$managed_path" ]; then
      printf 'not a managed link: %s\n' "$managed_path" >&2
      managed_links_ok=0
      continue
    fi
    readlink "$managed_path"
  done
fi

if [ "$managed_links_ok" -ne 1 ]; then
  printf 'STOP: do not run execution-level checks\n' >&2
  false
fi
unset managed_links_ok managed_path profile_source starship_profiles_source

zsh_config_dir=$(zsh -c 'print -r -- "${ZDOTDIR:-$HOME}"')
zsh -n "$HOME/.zshenv"
zsh -n "$zsh_config_dir/.zprofile"
zsh -n "$zsh_config_dir/.zshrc"
```

这一层只能证明链接存在和文件可解析，不能证明被 source 的文件、插件或命令可用。

### 5.2 第二层：非交互、交互与登录

```sh
env -i HOME="$HOME" USER="$USER" LOGNAME="$LOGNAME" \
  PATH=/usr/bin:/bin:/usr/sbin:/sbin \
  /bin/zsh -c '
    printf "noninteractive ZDOTDIR=%s PATH=%s\n" "$ZDOTDIR" "$PATH"
    command -v git starship atuin zoxide fzf
  '

zsh -ic 'print "interactive-ok"; command -v starship atuin zoxide fzf'
zsh -lic '
  print "login-interactive-ok"
  print -r -- "active Starship config: ${STARSHIP_CONFIG:-$HOME/.config/starship.toml}"
'
```

非交互检查不应要求提示符、按键或 Antidote 函数存在；它只验证 `.zshenv` 和必要 PATH。`zsh -ic` 验证 `.zshrc`，`zsh -lic` 还加入 `.zprofile`。

登录交互启动成功还不等于生成位置正确。继续确认补全转储和 Antidote 静态脚本进入 XDG cache，且配置目录没有出现默认生成文件：

```sh
zsh -lic '
  cache_root="${XDG_CACHE_HOME:-$HOME/.cache}"
  for cache_path in \
    "$cache_root/zsh/zcompdump-$ZSH_VERSION" \
    "$cache_root/antidote/zsh_plugins.zsh"; do
    [[ -s "$cache_path" ]] || {
      print -u2 "STOP: expected cache missing or empty: $cache_path"
      exit 1
    }
  done

  for unexpected_path in \
    "$ZDOTDIR/.zcompdump" \
    "$ZDOTDIR/.zsh_plugins.zsh"; do
    [[ ! -e "$unexpected_path" ]] || {
      print -u2 "STOP: generated file leaked into ZDOTDIR: $unexpected_path"
      exit 1
    }
  done
'
```

若两处同时有补全转储，优先检查系统级 `zshrc` 是否在用户 `.zshrc` 之前执行裸 `compinit`；若 `.zsh_plugins.zsh` 落在清单旁边，检查是否仍有单参数 `antidote load`。先修正唯一调用路径，再移动旧缓存，不要靠删除后重启来掩盖重复初始化。

实际维护远程主机时，再从客户端执行一条真实的只读远程命令和一次新 SSH 登录。不要用本地 `env -i` 结果冒充网络、sshd 和账号策略已验证。

### 5.3 第三层：组件行为

```zsh
if (( $+functions[antidote] )); then
  antidote list
fi

atuin doctor

starship_config_root="$HOME/.config"
starship_config_files=("$starship_config_root/starship.toml")
if [[ -d "$starship_config_root/starship/profiles" ]]; then
  starship_config_files+=("$starship_config_root/starship/profiles/"*.toml(N))
fi
for starship_config in "${starship_config_files[@]}"; do
  [[ -s "$starship_config" ]] || {
    print -u2 "missing or empty Starship config: $starship_config"
    false
  }
  STARSHIP_CONFIG="$starship_config" starship explain >/dev/null
done
unset starship_config starship_config_files starship_config_root

zsh -lic '
  print -r -- "active Starship config: ${STARSHIP_CONFIG:-$HOME/.config/starship.toml}"
  starship explain >/dev/null
'
zoxide --version
fzf --version
bindkey '^R'
bindkey '^T'
time zsh -i -c exit
```

还应人工确认：

- `Ctrl-R` 只打开 Atuin，`Ctrl-T` 由 fzf 提供，`zi` 使用 zoxide；
- 自动建议与语法高亮没有重复或失效；
- Starship 的活动路径与实际外观一致，并在普通目录和大型 Git 仓库中都能及时出现；选择 Powerline profile 时字体图标没有方框或错位；
- Ghostty 能打开新窗口并重新加载配置，SSH 场景没有 terminfo 错误；
- dotfiles 工作树没有因为启动 Shell 而出现缓存、历史或本机数据。

组件行为验证完成后，重复第 5.1 节的目标类型检查。允许出现的新内容应位于 data、state 或 cache；若 `config.toml`、`starship.toml`、Starship profile、`config.ghostty` 等受管目标变成普通文件，应停止提交并追查是哪个初始化过程改变了所有权。

单次 `time` 受缓存影响，只适合发现明显退化，不是严格性能基准。

### 5.4 第四层：提交边界

只有适用场景通过后才审查并提交：

```sh
DOTFILES_DIR="$HOME/.dotfiles"

git -C "$DOTFILES_DIR" status --short --branch
git -C "$DOTFILES_DIR" diff --check
git -C "$DOTFILES_DIR" diff
git -C "$DOTFILES_DIR" diff --cached
```

二进制升级没有改变配置源时，dotfiles 没有新提交是正常结果。不要为了留下升级痕迹而修改无关时间戳或生成文件。

## 6. 按层隔离故障

从最外层到最内层逐步替换变量：

1. **终端层**：改用系统终端启动同一个 Zsh。只有 Ghostty 失败时，问题先限定在应用或配置。
2. **Shell 裸运行**：运行 `zsh -f`。它正常说明 Zsh 二进制基本可用，问题更可能在用户启动文件。
3. **启动文件层**：比较真实 `ZDOTDIR`，运行语法检查，查看最后一次配置 diff。
4. **插件层**：恢复 snapshot 或临时移除最后新增的一个 bundle，不删除整个插件目录。
5. **独立工具层**：分别运行 Atuin、Starship、zoxide、fzf 自检，不把所有异常归因于 Antidote。
6. **按键与提示符层**：搜索是否重复执行多个 `init`，并检查加载顺序。

| 症状 | 优先边界 | 第一动作 |
| --- | --- | --- |
| Ghostty 无法创建窗口 | 终端应用/配置 | 使用备用终端，检查 Ghostty 配置 |
| `zsh -f` 正常，新 Shell 失败 | 启动文件 | `zsh -n` 与最近配置 diff |
| 只有补全失败 | `fpath` / `compinit` | 确认补全插件在 `compinit` 前 |
| `$ZDOTDIR` 出现 `.zcompdump` 或 `.zsh_plugins.zsh` | 系统级或重复的默认初始化 | 搜索系统与用户启动文件中的 `compinit`、`antidote load`，确认唯一所有者 |
| 只有高亮失败 | ZLE 加载顺序 | 确认高亮在其他交互工具之后 |
| `Ctrl-R` 行为错误 | fzf/Atuin 重复绑定 | 检查两个 init 与 `bindkey '^R'` |
| IDE 中 Atuin 不记录 | 不是交互 Shell或钩子缺失 | 在该终端运行 `atuin doctor` |
| Stow 突然报告 Atuin/Ghostty 配置冲突 | 应用先生成普通配置 | 保留文件并比较，不用 `--adopt`；恢复“先源、后 Stow、再初始化”的顺序 |
| 大型仓库提示符变慢 | Starship 模块 | 运行 `starship timings` |
| SSH 报 unknown terminal | 远端 terminfo | 按 [[Ghostty 常用配置与 Shell 集成]] 排查 |

## 7. 回退必须匹配发生变化的层

### 7.1 配置内容

受管目标是符号链接，内容事实来源在 dotfiles。先保存当前证据：

```sh
DOTFILES_DIR="$HOME/.dotfiles"
git -C "$DOTFILES_DIR" status --short --branch
git -C "$DOTFILES_DIR" diff
git -C "$DOTFILES_DIR" log --oneline --decorate -10
```

已推送的错误提交优先使用 `git revert` 保留历史。未提交实验只对明确文件恢复，并在操作前保存差异；不要用 `git reset --hard` 清理整个仓库。恢复内容后先语法检查，再开新 Shell；只改内容通常不需要重新 Stow。

Starship 只是选错活动 profile 时，不需要回退配置内容或部署关系：清除当前 Shell 的 `STARSHIP_CONFIG`，或从不入库的 `local.zsh` 删除该选择，再执行 `exec zsh -l` 即可回到默认配置。只有某份 TOML 本身有误时才恢复那一份明确源文件；不要复制 profile 覆盖默认文件，也不要替换 Stow 链接。

### 7.2 Stow 部署关系

新增、移动或删除源路径造成链接异常时，对实际软件包先模拟 `--restow`。需要完全解除时，先模拟 `--delete`，确认只删除该软件包拥有的链接后再应用。完整边界见 [[使用 Git 与 GNU Stow 搭建 dotfiles 仓库#12. 回退分成内容与部署两件事]]。

### 7.3 Antidote 插件

```zsh
DOTFILES_DIR="$HOME/.dotfiles"
snapshot_source="$DOTFILES_DIR/zsh/.config/zsh/snapshots/antidote.txt"
antidote snapshot restore "$snapshot_source"
```

恢复后新开 Shell验证。若清单本身也改变，必须把 `.zsh_plugins.txt` 恢复到同一配置版本，否则下次加载会再次改变插件集合。

### 7.4 单个二进制

使用原包管理器或安装来源提供的固定、降级或回滚方式，只回退该组件并保留用户配置。不要为了回退 Starship 或 fzf 删除整个 Zsh 配置，也不要为了回退 Ghostty 修改远端服务器。

### 7.5 Atuin 数据

Atuin 数据恢复不是配置回退：先临时禁用 `atuin init`、关闭其他交互 Shell，再从受保护备份恢复实际数据目录，最后重新启用并运行 `atuin doctor`。同步用户必须持有原加密密钥；密钥丢失不能靠 Git 或重新登录恢复。

## 8. 本文不承担新机器恢复

新机器恢复包含平台依赖、远端 clone、冲突基线、package 选择、local 文件、登录 Shell 与真实 SSH 验收，是一条完整场景主线。统一执行 [[从已有 dotfiles 恢复现代终端环境]]，不要从维护章节拼装另一条恢复流程。
