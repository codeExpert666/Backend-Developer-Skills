本文解释 Linux 为什么从一棵以 `/` 为起点的目录树组织文件，常见系统目录分别承担什么职责，以及面对配置、程序、日志、服务数据、运行时文件和临时文件时，应怎样判断合适的放置位置。

本篇只建立目录职责、生命周期和管理边界。路径如何被 Shell 解析见 [[Shell 路径、变量、引用与展开]]，文件操作命令见 [[Linux 文件与目录常用命令]]，目录权限见 [[Linux 用户、用户组、sudo 与文件权限]]，目录背后的文件系统与块设备见 [[Linux 磁盘、分区、文件系统与 LVM 基础]]。

> [!abstract] 本篇掌握目标
> - **必须熟练**：区分 `/` 与 `/root`、`/usr` 与用户主目录、`/etc` 与 `/var`、`/run` 与持久数据，并知道普通用户不应随意写入系统目录。
> - **理解会查**：按“管理者、是否变化、是否持久、是否可重建”判断内容应位于用户目录、系统配置、软件资源、服务状态、运行时目录还是临时目录。
> - **认识即可**：Filesystem Hierarchy Standard（文件系统层次结构标准，FHS）、`/usr` 合并、虚拟 API（Application Programming Interface，应用程序接口）文件系统以及发行版差异；遇到具体机器时使用只读命令核对。

> [!info] 资料核对日期与证据边界
> 本文于 **2026-08-30** 核对 FreeDesktop 当前发布的 FHS 3.0（发布日期 2026-04-08）、Linux man-pages（Linux 手册页项目）6.18 的 `hier(7)`、Debian Policy（Debian 策略手册）4.7.4.1 的文件系统层次规则，以及现代布局参考 UAPI.9 Linux File System Hierarchy（Linux 文件系统层次）。UAPI.9 当前标为 **0.1、Work in progress（工作草案）**，本文只用它补充现代布局方向，不把它当作已经取代 FHS 的稳定标准。具体发行版、容器和主机仍应以自身策略、软件文档和只读输出为准。

## 1. 先区分路径、目录职责和存储来源

Linux 向进程呈现一棵统一目录树，最顶层是根目录 `/`。绝对路径从 `/` 开始逐级查找，例如 `/var/log/app.log`；但“从 `/` 开始”只说明路径如何解析，不代表路径中的全部内容都来自同一个磁盘、分区或文件系统。

一个路径至少需要从三层理解：

| 层次 | 回答的问题 | 典型检查或知识入口 |
| --- | --- | --- |
| 路径解析 | 这段路径从哪里开始、每一级名称是什么 | `pwd`、`realpath`；[[Shell 路径、变量、引用与展开]] |
| 目录职责 | 这里通常应该保存配置、程序、日志、状态还是临时数据 | FHS、发行版策略、当前软件官方文档 |
| 存储来源 | 这条路径实际落在哪个挂载点和文件系统上 | `findmnt --target`；[[Linux 磁盘、分区、文件系统与 LVM 基础]] |

例如，`/home` 通常承担普通用户主目录的职责，但它既可能位于根文件系统，也可能是单独挂载的本地文件系统或网络文件系统。目录名表达约定用途，不能单独证明存储来源、权限、容量或持久性。

## 2. FHS 是基线，不是当前机器的完整清单

FHS 规定许多 Unix-like（类 Unix）系统中目录与文件的放置原则，目的是让应用、管理工具、脚本和文档能够预期常见位置。它适合回答“这个目录为什么存在、通常由谁管理”，但不应被理解为以下保证：

- 每个发行版都完整采用相同目录和相同实现。
- 标准中的可选目录必然存在。
- 同名目录一定是普通磁盘目录，而不是符号链接或挂载点。
- 容器、只读系统、临时系统和传统主机拥有完全相同的布局。
- 某个软件一定使用通用默认位置，而没有发行版或管理员覆盖。

判断实际路径时按以下证据顺序进行：

1. **目录的通用职责**：先查 FHS、`hier(7)` 等标准或手册。
2. **发行版实现**：再查目标发行版的策略、软件包布局和版本文档。
3. **软件自己的约定**：确认应用配置、服务单元、启动参数和包管理器实际采用的路径。
4. **当前主机状态**：最后使用 `ls`、`readlink`、`findmnt`、`stat` 等只读命令核对。

这四层出现差异时，不应把旧目录表强行套到当前系统，也不应只凭当前一台机器的输出改写为跨发行版结论。

## 3. 常见目录按什么职责分工

### 3.1 根、启动、用户与系统配置

| 路径 | 主要职责 | 关键边界 |
| --- | --- | --- |
| `/` | 整棵目录树的起点 | 它是路径概念；根目录下还可以接入其他文件系统 |
| `/boot` | 内核、initramfs（initial RAM filesystem，启动早期使用的内存文件系统镜像）、引导加载器等启动所需资源 | 可能位于独立文件系统；不要把它当普通资料目录或手工清理 |
| `/home` | 普通用户主目录的常见上级目录 | 程序应优先从账户信息或 `$HOME` 获取实际主目录，不硬编码 `/home/用户名` |
| `/root` | root（超级用户）的主目录 | 它不是根目录 `/`，也不适合作为普通用户工作区 |
| `/etc` | 当前主机的系统级配置 | 不用于保存不断增长的日志、缓存、数据库或普通可执行程序 |

`/etc` 中的文件会影响当前主机行为，但“配置文件位于 `/etc`”不等于直接修改一定安全。写入前仍需确认软件的加载顺序、语法检查、权限、备份和恢复方法；某些软件还会从多个片段目录合并最终配置。

### 3.2 系统软件、管理员本地软件与附加软件

| 路径 | 主要职责 | 常见管理者与边界 |
| --- | --- | --- |
| `/usr` | 操作系统或发行版提供的程序、库和静态资源 | 通常由包管理器管理，不应手工改写包内文件 |
| `/usr/bin` | 可从 Shell 调用的常用命令 | 实际命令位置应使用 `command -v` 核对 |
| `/usr/sbin` | 传统上放置系统管理命令 | 是否单独存在、是否进入普通用户的 `PATH` 命令查找路径，取决于发行版与环境 |
| `/usr/lib` | 库、软件私有资源和内部程序 | 多架构系统还可能使用带架构标识的子目录 |
| `/usr/share` | 与处理器架构无关的共享资源 | 常见内容包括手册、文档、时区和字体 |
| `/usr/local` | 当前站点或管理员在发行版包管理之外维护的本地层次 | 通常由管理员管理，并按 `bin`、`lib`、`share` 等继续分层 |
| `/opt` | 可选或第三方附加软件包的常见位置 | 是否采用以及内部结构应服从软件和发行版文档，不把它当任意工具堆放区 |

这里的 `/usr` 不是“某个用户的目录”，普通用户的个人文件通常位于 `$HOME`。`/usr/local` 与 `/opt` 也不是同义词：前者属于管理员维护的本地层次，后者常由一个附加软件包或供应方占用独立子目录。选择安装位置时，应优先遵守发行版包管理和软件官方安装方式，不能只凭目录名称自行搬动文件。

#### `/bin`、`/sbin`、`/lib` 为什么可能是符号链接

传统 FHS 将启动和修复系统所需的命令与库放在根目录下的 `/bin`、`/sbin`、`/lib`。许多现代发行版采用 `/usr` 合并，让这些路径成为指向 `/usr` 中相应位置的兼容符号链接；其他系统仍可能保留独立目录。

因此应把它们理解为稳定的兼容路径，而不是先假定磁盘上保存了两份程序。使用 `ls -ld` 和 `readlink -f` 核对当前系统，不要手工删除、替换或重建这些系统级链接。

### 3.3 `/var`：需要变化并通常应持久保存的系统数据

`/var` 的核心含义是 variable data（会变化的数据），不是“价值较低、可以随意删除的数据”。数据库状态、软件包状态、队列和审计日志都可能位于其中。

| 路径 | 主要职责 | 删除或迁移前必须知道什么 |
| --- | --- | --- |
| `/var/lib` | 服务和系统组件的持久私有状态 | 可能包含数据库、软件包状态或节点身份，通常不能靠重装自动恢复 |
| `/var/log` | 持久日志的常见位置 | 有些系统主要使用 systemd（系统与服务管理器）的 journal（日志存储）；日志也可能含地址、请求参数或凭据片段 |
| `/var/cache` | 丢失后原则上可重新生成的系统缓存 | 重建仍有网络、时间和可用性成本，应使用软件支持的清理方式 |
| `/var/spool` | spool（等待后续处理的队列）数据 | 邮件、打印或定时任务队列不是普通缓存，盲删可能丢失待处理工作 |
| `/var/opt` | 安装在 `/opt` 下的软件所使用的可变数据 | 只有目标软件采用这套布局时才使用 |

同一个服务可以把静态程序放在 `/usr`，主机配置放在 `/etc`，持久状态放在 `/var/lib`，日志交给 journal 或 `/var/log`。这些位置共同组成服务，不应因为目录分散就手工合并。

### 3.4 运行时数据与临时文件

运行时数据常包含 PID（Process ID，进程标识）和 socket（套接字）。它们描述当前启动或当前会话中的活动对象，不是需要长期保存的业务数据。

| 路径 | 生命周期 | 适合内容 | 不适合内容 |
| --- | --- | --- | --- |
| `/run` | 从本次启动开始，通常在重启后清空 | PID、socket、锁和启动后生成的运行时状态 | 需要跨重启保留的数据和人工维护的静态配置 |
| `/tmp` | 短期临时；可能在启动时或按清理策略删除 | 当前任务的临时文件和目录 | 源码唯一副本、备份、数据库和长期交换文件 |
| `/var/tmp` | 通常比 `/tmp` 保留更久，常可跨一次重启 | 生命周期较长但仍可丢弃的临时文件 | 永久数据；清理策略仍可能删除旧文件 |

`/var/run` 在许多现代系统上是指向 `/run` 的兼容路径。不要同时把两者当成独立的数据位置。

`/tmp` 和 `/var/tmp` 往往允许多个用户写入。sticky bit（粘滞位）会限制用户删除其他用户拥有的目录项，但不会自动解决可预测名称、符号链接竞争或敏感内容泄露。脚本应使用 `mktemp` 或应用提供的安全临时文件接口，不自行拼接固定文件名。

### 3.5 设备与内核提供的虚拟 API 文件系统

| 路径 | 主要职责 | 为什么不是普通数据目录 |
| --- | --- | --- |
| `/dev` | 设备节点和部分进程间通信接口 | 通常由内核与设备管理组件共同维护，不用于保存普通文件 |
| `/proc` | 进程、内核状态和部分可调参数的接口 | 多数内容由内核动态生成，重启后重新出现 |
| `/sys` | 设备、驱动和其他内核对象接口 | 它表达当前内核视图，不是普通配置仓库 |

读取这些路径可能是在调用内核接口，而不只是打开磁盘上的静态文本。写入 `/proc/sys` 或 `/sys` 可能立即改变系统行为；本篇只把它们作为目录地图介绍，不提供写操作。需要持久配置时，应查目标功能支持的配置机制，而不是把一次直接写入误认为已经持久化。

### 3.6 服务数据与挂载入口

| 路径 | 主要职责 | 关键边界 |
| --- | --- | --- |
| `/srv` | 当前站点对外提供的服务内容 | 并非所有服务都采用；服务私有状态也可能属于 `/var/lib` |
| `/mnt` | 管理员临时挂载文件系统的传统入口 | 临时挂载不等于临时数据，挂载内容本身可能非常重要 |
| `/media` | 可移动介质挂载点的传统入口 | 桌面环境和发行版也可能使用其他自动挂载路径，应以 `findmnt` 为准 |

还可能看到 `/efi`、`/snap`、`/lost+found` 等目录。它们分别可能来自启动方案、发行版软件机制或特定文件系统实现，不应仅因出现在某台机器上就扩展成所有 Linux 系统的必备目录。

## 4. 面对新内容时怎样选择位置

先判断“谁管理、是否变化、是否持久、能否重建”，再选择路径。用户级配置、数据、状态和缓存还可能遵循 XDG Base Directory Specification（XDG 基础目录规范）；它只约定用户目录职责，不取代系统级 FHS，现有终端环境中的应用方式见 [[现代终端环境搭建概览]]。

下表中的 `PROJECT_NAME`、`APP_NAME`、`SERVICE_NAME`、`PRODUCT_NAME` 和 `MOUNT_NAME` 是说明性名称，不是可以原样执行的 Shell 变量或固定目录。`TMPDIR`（temporary directory，临时目录）则是真实的环境变量，其展开规则在表后单独解释。

| 内容 | 常见方向 | 决策说明 |
| --- | --- | --- |
| 个人源码和 Git 工作树 | `$HOME/src/PROJECT_NAME` | 这是个人工作区约定，不是 FHS 强制标准；详见 [[Linux 开发工作区与本地文件系统规划]] |
| 用户级应用配置 | `$HOME` 下应用支持的位置或 XDG 配置目录 | 先查应用是否支持 XDG 和现有配置，不自行迁移后假定应用会读取 |
| 当前主机的系统级配置 | `/etc/APP_NAME/` 或软件声明的位置 | 由管理员维护，修改前检查加载顺序、语法、备份和恢复 |
| 管理员本地安装的命令 | `/usr/local/bin` 等本地层次 | 仅在不使用发行版包或受管理安装工具时考虑，并记录来源和升级方法 |
| 独立附加软件包 | `/opt/PRODUCT_NAME/` 或供应方指定位置 | 服从该软件的安装、配置和卸载约定 |
| 服务持久状态 | `/var/lib/SERVICE_NAME/` 或服务实际配置 | 可能不可重建；迁移前停止写入、备份并使用服务支持的方法 |
| 服务日志 | journal、`/var/log/SERVICE_NAME/` 或服务实际配置 | 日志去向由服务和系统日志方案决定，不手工假定只有一种位置 |
| 可重建系统缓存 | `/var/cache/SERVICE_NAME/` | 清理前确认缓存性质和官方清理入口 |
| 等待处理的队列 | `/var/spool/SERVICE_NAME/` | 不是普通缓存，删除可能丢失任务或消息 |
| 进程标识、套接字和运行时状态 | `/run/SERVICE_NAME/` | 应由服务启动、systemd 或系统的临时文件管理机制创建，不靠人工永久预建 |
| 当前站点提供的服务内容 | `/srv/SERVICE_NAME/` | 只在部署设计明确采用时使用，并与服务私有状态分开 |
| 当前任务的临时对象 | `${TMPDIR:-/tmp}` 下由安全接口创建的位置 | 不依赖固定名称，不作为长期存储 |
| 临时挂载文件系统 | `/mnt/MOUNT_NAME/` 或发行版约定位置 | 先确认真实设备、文件系统和卸载条件，再执行挂载 |

这个表只用于先找到正确方向。软件包、数据库、容器运行时和系统服务都可能有自己的目录、权限、标签和迁移要求；通用目录规范不能替代目标软件文档。

`${TMPDIR:-/tmp}` 是 Shell 的默认值展开：`TMPDIR` 已设置且非空时使用其值，否则使用 `/tmp`。它只选择临时目录起点，真正创建对象时仍应使用 `mktemp` 等安全接口；展开语法见 [[Shell 路径、变量、引用与展开]]。

## 5. 用只读命令核对当前主机

下面的检查只读取目录项、符号链接和挂载信息，不创建、修改或删除文件，也不使用 `sudo`。

**执行位置：Linux 主机（任意目录，只读）**

```bash
for CHECK_PATH in \
  / /boot /dev /etc /home /root /run /tmp /usr /usr/local /var \
  /opt /srv /mnt /media /proc /sys; do
  if [ -e "$CHECK_PATH" ] || [ -L "$CHECK_PATH" ]; then
    ls -ld -- "$CHECK_PATH"
  else
    printf 'MISSING: %s\n' "$CHECK_PATH"
  fi
done

for CHECK_PATH in /bin /sbin /lib /lib64 /var/run; do
  if [ -L "$CHECK_PATH" ]; then
    if LINK_TARGET="$(readlink -f -- "$CHECK_PATH")"; then
      printf 'LINK: %s -> %s\n' "$CHECK_PATH" "$LINK_TARGET"
    else
      printf 'FAIL: 无法解析符号链接：%s\n' "$CHECK_PATH" >&2
    fi
  elif [ -e "$CHECK_PATH" ]; then
    printf 'NOT_LINK: %s\n' "$CHECK_PATH"
  else
    printf 'MISSING: %s\n' "$CHECK_PATH"
  fi
done

if command -v findmnt >/dev/null 2>&1; then
  for CHECK_PATH in / /run /tmp /var /dev /proc /sys; do
    if [ -e "$CHECK_PATH" ]; then
      findmnt -o SOURCE,FSTYPE,OPTIONS,TARGET --target "$CHECK_PATH" ||
        printf 'FAIL: 无法读取挂载信息：%s\n' "$CHECK_PATH" >&2
    fi
  done
else
  printf '%s\n' 'SKIP: 当前 PATH 中没有 findmnt。'
fi
```

按以下顺序解释结果：

1. `ls -ld` 查看目录项本身，不进入目录枚举内容；缺少可选目录只说明当前系统没有该路径。
2. `readlink -f` 解析兼容符号链接的最终目标；`NOT_LINK` 表示当前路径存在但不是符号链接，不能据此判断系统错误。
3. `command -v findmnt` 先确认当前命令查找路径中存在 `findmnt`；存在时，`findmnt --target` 再查找包含目标路径的文件系统。`SOURCE`、`FSTYPE`、`OPTIONS` 和 `TARGET` 分别说明来源、类型、挂载选项和挂载点。
4. `/run`、`/dev`、`/proc`、`/sys` 显示为 `tmpfs`（临时内存文件系统）、`devtmpfs`（设备节点文件系统）、`proc` 或 `sysfs`（内核虚拟文件系统）等类型时，说明它们通过专用文件系统接入目录树，不是普通磁盘目录的固定答案。

本机安装了相应手册时，还可以只读查看：

```bash
man 7 hier
man 7 file-hierarchy
```

某个手册不存在，只说明当前系统没有安装该手册页；应转向发行版或上游官方文档，不能把缺少手册误判为目录规范不存在。

## 6. 实际路径与预期不一致时怎么办

发现服务没有使用预期目录、目录变成符号链接或路径位于意外挂载点时，先保留现场，不直接移动、删除或重新创建：

1. 使用 `ls -ld`、`readlink -f`、`stat`、`namei -l` 和 `findmnt --target` 确认对象、链接、逐级权限和挂载来源。
2. 确认该文件由发行版软件包、管理员、当前用户、服务还是内核接口管理。
3. 阅读应用配置、启动参数和服务单元，区分默认路径、实际有效路径与运行时生成路径；systemd 的来源和生效边界见 [[systemd 服务与日志基础]]。
4. 若涉及数据库、队列、容器卷、身份状态或日志，先确认一致性要求、停止写入条件、备份和恢复方法。
5. 只有在目标软件支持迁移且已经建立可恢复副本后，才设计单独的变更流程；迁移完成还要验证服务功能和旧路径是否仍被引用。

当前主机的一次性目录输出、发行版版本和迁移结果属于日期化执行证据，不应原样写进这篇可复用通用笔记。

## 7. 常见误解

| 误解 | 正确认识 |
| --- | --- |
| `/root` 就是根目录 | `/` 是目录树起点；`/root` 通常是 root 用户的主目录 |
| `/usr` 用来保存普通用户文件 | `/usr` 主要承载系统或发行版提供的软件资源；用户文件通常在 `$HOME` |
| 绝对路径都位于根文件系统 | 绝对路径只说明从 `/` 解析；途中可以跨入其他挂载点 |
| `/var` 中的内容都可以清理 | `/var/lib`、`/var/spool` 等可能包含持久状态和待处理工作 |
| `/run` 适合保存配置 | `/run` 保存本次启动的运行时数据，通常会在重启后清空 |
| `/tmp` 有 sticky bit 就能保存敏感或长期数据 | sticky bit 只限制部分删除和重命名行为；名称竞争、读取权限和清理策略仍需单独处理 |
| `/usr/local` 与 `/opt` 可以随意互换 | 两者管理边界不同，选择应服从发行版与软件安装方式 |
| `/bin` 和 `/usr/bin` 一定保存两份程序 | 现代系统中 `/bin` 可能只是指向 `/usr/bin` 的兼容链接 |
| 所有日志一定能在 `/var/log` 找到 | 服务可能使用 journal、远端日志或自定义位置，应检查实际日志方案 |
| 所有 Linux 发行版都应与 FHS 目录表逐项一致 | FHS 是基线；发行版、容器和现代布局会有明确例外和扩展 |

## 完成标准

- [ ] 能解释路径位置、目录职责与存储来源是三个不同问题。
- [ ] 能区分 `/`、`/root`、`/home`、`/etc`、`/usr`、`/usr/local` 和 `/opt` 的主要职责。
- [ ] 能区分 `/var/lib`、`/var/log`、`/var/cache`、`/var/spool` 与 `/run` 的生命周期。
- [ ] 知道 `/dev`、`/proc` 和 `/sys` 是设备或内核 API 边界，不是普通数据目录。
- [ ] 知道 `/tmp` 与 `/var/tmp` 都不是永久存储，并会使用安全的临时文件接口。
- [ ] 遇到 `/bin`、`/sbin`、`/lib` 和 `/var/run` 时，会先检查是否为兼容符号链接。
- [ ] 能先按管理者、变化性、持久性和可重建性选择目录方向，再查目标软件文档。
- [ ] 实际路径不符合预期时，会先只读取证并设计恢复，不直接搬移系统或服务数据。
